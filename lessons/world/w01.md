## 火箭和医疗器械里面，也有计算机

**程序始终需要能够执行它的物理计算装置；火箭和医疗器械里本来就可以装有这样的计算机。**我们平时把“计算机”当成显示器、键盘和主机箱的组合，其实让程序运行的关键是处理器、存储器、供电、时钟，以及与外界交换信号的接口。屏幕和鼠标是某些计算机的交互设备，不是计算机执行程序的必要条件。

家用电脑面向很多用途：浏览网页、写文档、看视频。设备中的计算机通常围绕特定功能设计，称为**嵌入式系统**。一台输液泵可能需要读取传感器、控制电机、显示设置和发出报警；一台飞行计算机可能需要读取惯性测量、计算状态、控制执行机构并与其他系统通信。它们都在执行指令，只是外壳、接口、算力、功耗、可靠性与时间要求不同。

不是整枚火箭的金属外壳在“读代码”，也不是电极自己理解 Java。里面的控制计算机或专用控制器运行软件，软件经接口影响其他部件。一台复杂设备还可能有多颗处理器：负责屏幕的系统与负责实时控制的控制器各自运行软件，通过明确协议交换数据。

**微控制器 MCU**常把处理器核心、片上存储和定时器、模数转换、通信等外设集成在一颗芯片上。它可以很小、很省电，但仍然有取指与执行能力。微处理器配合外部存储、SoC、专用数字信号处理器等也都可出现在嵌入式设备中。并非每台设备都采用 MCU，也并非所有电子电路都是通用计算机：有的功能由模拟电路、固定逻辑或可编程逻辑实现。

## 运行程序的是 CPU，操作系统管理运行环境

CPU 的硬件电路根据指令集取出指令、译码并执行。程序计数器记录下一处取指位置，寄存器与存储器保存状态；加法、比较、跳转等操作依靠电路完成。**执行这套机制不需要先有一个 Windows。**操作系统本身也是软件，它的启动代码同样先由处理器执行，而不是由另一个无限后退的操作系统“帮它运行”。

操作系统提供任务或进程调度、资源管理、设备访问、通信与文件等服务；具体提供哪些功能取决于设计。桌面图标、窗口、文件管理器只是我们熟悉的某种使用界面。没有桌面不等于没有操作系统；没有操作系统也不等于没有软件、驱动或中断。

| 运行方式 | 大致路径 | 谁安排工作 | 应怎样理解 |
| --- | --- | --- | --- |
| 桌面或通用操作系统 | 启动软件 → 内核与服务 → 应用 | 操作系统与应用共同安排 | 常见于个人电脑，也可用于设备里的某些子系统 |
| 嵌入式 Linux 等 | 启动软件 → 内核 → 服务与应用 | 内核调度及应用逻辑 | 可以完全没有桌面；通常需要相应内存与硬件支持 |
| 实时操作系统 RTOS | 启动例程 → 初始化任务 → 内核调度 | RTOS 调度任务，应用定义优先级等 | 强调满足规定时间约束；不是“天然比 Linux 快且永不超时” |
| 裸机 bare-metal | 复位入口 → 启动例程 → 主循环或事件处理 | 应用、硬件中断与外设协作 | 没有操作系统内核，但仍有机器指令与初始化代码 |

医疗器械与火箭**有的有操作系统，有的没有，同一个系统还可能混用几种方式**。不能仅凭“医疗”“航天”就断言采用哪一种，也不能把 RTOS 当作某一款统一产品。选择取决于具体功能、处理器、功耗、任务复杂度、时间约束与验证要求。小型植入设备与大型医疗影像工作站，也不应被想象成相同架构。

## 没有操作系统，上电后的第一条指令从哪来

处理器的设计规定了复位后如何找到启动入口。有些芯片先执行片上 ROM 中的引导代码；有些微控制器依照复位向量表取得初始栈指针和复位处理函数地址；具体方式依芯片架构和启动配置而定。**不是必须先有操作系统把程序加载起来，硬件本来就定义了最早的启动规则。**

以常见 MCU 固件思路为例，可以沿下面的链路理解。它是通用讲解，不是每款芯片都完全一致的启动时序：

1. **供电与复位**：电源和必要的时钟条件满足后，处理器按硬件规则进入复位入口。软件之后仍可能配置工作时钟，不能把“配置高速时钟”说成此前完全没有时钟。
2. **选择启动路径**：按芯片配置从某种存储介质或引导入口继续。某些系统验证镜像、选择 A/B 分区或进入恢复模式，但这些能力需要相应设计，不是所有芯片天然拥有。
3. **准备运行环境**：启动代码设置必要的栈与处理器状态；按链接布局将带初值的数据复制到运行位置，清零应零初始化的数据区，并进行所需初始化。通常称为 `.data`、`.bss` 的区域有各自约定，不能理解为“随便把全部 RAM 清空”。有些工作由汇编启动代码做，有些由语言运行库做。
4. **初始化硬件与应用**：配置需要使用的 GPIO、定时器、ADC、通信接口等，再进入应用入口。`main` 是许多工具链采用的语言层入口，不一定是上电时 CPU 执行的第一条指令。
5. **持续完成任务**：裸机可反复采样、计算、更新输出，也可结合中断与休眠工作；采用 RTOS 则初始化任务并启动内核调度。常驻固件通常不会像桌面小程序那样算完就返回一个现成的命令行窗口。

因此“没有操作系统”并不是“没有启动过程”，而是启动例程和应用直接承担了更多职责。反过来，一套 RTOS 也可能与应用一起链接成一个固件镜像，而不以桌面式“每个程序一个独立进程”的方式存在；内存隔离是否具备，需要看硬件和系统配置，不能只看 RTOS 这个名字。

## 固件、Flash、RAM：程序住在哪里

开发者在电脑上编辑源代码，通过面向目标处理器的编译器生成目标文件，再由链接器组织代码、数据与地址布局，形成可部署镜像。编译器与链接器运行在开发电脑上，生成的是给目标芯片执行的内容，这叫**交叉编译**。程序通过工厂烧录、调试接口或经过设计的更新机制写入设备。设备之后可以离开开发电脑，自己从非易失存储启动。

Flash、ROM 等介质可以在断电后保留固件；RAM 常用于运行时变量、栈和缓冲，通常断电丢失。某些芯片可直接从 Flash 取指，另一些系统会先将代码装入 RAM 或其他可执行存储。启动并不总等于“从硬盘复制一个 EXE 到内存”，也不是所有设备都没有文件系统。

固件是紧密服务于设备的软件，可能包括启动、驱动、应用以及操作系统内核。它不意味着永不更新，也不意味着某种神秘的新语言。C、C++、Rust、汇编等可生成面向目标的本机代码；有的设备也提供解释器或虚拟机。

写成 Java 的程序通常需要相应 JVM 与库支持，JavaScript 通常需要执行引擎；特定系统也可能采用预先编译等方案。不能把桌面 EXE、JAR 或网页脚本随便复制到任意芯片就指望它运行。**指令集、二进制格式、运行库、内存布局和设备接口必须匹配。**同一段算法可以移植，现成文件并不因此通用。

## 没有键盘鼠标，程序怎样和器械打交道

输入可能来自电压、温度、加速度、电信号、按钮或通信消息。ADC 把模拟信号转换成数字采样；定时器提供时间事件；总线控制器与传感器交换数据。驱动代码知道如何使用这些接口，驱动也可以存在于裸机固件里，不一定属于操作系统。

一种常见方式是**内存映射 I/O**：处理器对某个约定地址读写时，硬件地址译码把访问送给外设寄存器，而不是普通 RAM。例如写某个输出寄存器，可以改变引脚逻辑或启动外设动作。具体地址、位含义与允许顺序由芯片手册规定；误写地址不是“随便设置另一个变量”。实际产品还可能通过专用 I/O 指令、总线、DMA 或其他控制器协作。

寄存器输出的信号再交给驱动电路、电机、阀门或刺激电路。供能来自设备的电源，CPU 的逻辑决定动作条件与时机。真实设备还需考虑电气隔离、反馈与互锁，不是代码把一个变量设成 1，物理装置就必然按理想方式完成动作。

## 中断不是操作系统的专利

裸机程序可以主动循环查询设备状态，叫轮询；也可以让定时器或外设产生中断请求。处理器在允许受理时保存必要上下文，进入预先设置的中断处理程序，再按架构规则返回。是否能受理还受屏蔽、优先级与当前状态影响，中断不是“无条件马上执行”的承诺。

一个常见思路是：中断处理只保存数据或设置事件标志，让主循环或任务稍后完成较长计算。RTOS 可以在中断后唤醒任务并安排调度，具体调用限制由该 RTOS 规定。中断属于硬件与软件共同支持的机制，**有无操作系统，与有无中断，是两个不同问题**。

没有操作系统不自动意味着更安全或更快。裸机代码依然可能死循环、越界、错过事件；RTOS 也不能自动消除竞态、优先级配置错误或共同软件缺陷。后面医疗互锁、实时调度和航天事故章节，就是在进一步分析这些问题。

## 自测：没有操作系统，谁让第一段程序运行

答：硬件定义复位与取指规则，存储中已有可执行入口与代码。启动代码再准备后续环境。操作系统自身也是沿着某条启动链被执行的软件，因此不是所有程序都必须先依靠另一个操作系统。

问：飞行计算机上能直接运行我电脑的程序吗？答：取决于架构与环境是否匹配。即使算法相同，目标指令集、运行时、外设与验证要求仍可能要求重新编译或移植。问：看到没有桌面界面，能断定没有 OS 吗？答：不能，无界面的 Linux、RTOS 和裸机在外观上都可能没有桌面。

进一步可读 [Arm 开发者文档](https://developer.arm.com/documentation)中的目标架构与芯片启动说明，以及 [FreeRTOS 官方网站](https://www.freertos.org/)的内核与任务文档。具体设备是否采用某款处理器或 RTOS，须查该设备资料，不能从行业名称推断。

## 为什么一行文字能让电梯移动

你按下电梯的“5”，手指没有抬起几吨重的轿厢。按钮改变电路信号，控制器把信号编码成请求，程序结合当前位置、方向、门锁和任务队列决定动作，驱动装置再调节电机。推动轿厢的能量来自电力；代码规定能量何时、以何种条件被使用。把“信息”和“能量”分开，就不容易把编程理解成魔法。

程序是对信息进行有限步骤处理的规则。变量像带标签的格子，条件像岔路，循环像不断巡视的值班员，函数像有输入和输出的工作站。这个比喻能帮助入门，但格子里存的是编码后的数值，不是温度、病人或飞船本身。温度传感器坏了，变量仍可能装着一个语法完全合法的数字。

物理世界到代码之间有一座桥：传感器把温度、光、电压或加速度转换成可测信号；采样与转换得到离散数据；程序计算；执行器把指令转换成阀门、电流、电机转矩等动作。动作又改变下一次测量。**感知—计算—执行—再感知**形成闭环。只发一次命令而不看后果，叫开环，未必错误，但适用条件不同。

## 先看一台不会伤人的虚拟恒温箱

想象在家给面团发酵。目标 22°C，当前 18°C。最直觉的规则是“越冷，开得越大”。我们设误差 e=目标−测量，功率指令 u=增益×e，再把 u 限制在 −4～4。负数在本模型代表制冷，正数代表加热。设备不能无限输出，所以限幅是规则的一部分。

每次采样之后，温度按“原温度 + 0.5×功率 − 0.07×高于环境的温差”更新。这是人为选定的离散教学方程，环境恒为 18°C，采样间隔归一化。系数不来自某款真实恒温设备，也不能作为医疗或工业控制参数。我们保留散热，是为了让你看见：程序动作之外，还有环境在改变结果。

为什么最后不一定精确到 22？纯比例控制需要保留一点误差，才能持续提供抵消散热的功率。到 22 时若误差为零，功率也为零，箱子就会降温。这个稳态偏差提示我们改进控制器的方向，例如积分项；但积分会引入累积与饱和问题，不能只在公式上多加一个字母就认为万事大吉。

## 延迟怎样让好意变成来回折腾

你洗澡时觉得水冷，拧大热水；管道中的热水还没到，又拧大一次。稍后烫起来，再猛关。你处理的是旧反馈，却以为自己在看“现在”。控制器也会这样：增益大、测量旧、动作频繁，可能超调甚至持续振荡。

实验中的 delay=3 表示用三个采样以前的历史读数，绝不是把浏览器卡顿当物理延迟。增益变大不一定让“更快而且更稳”；目标变化、噪声、执行器限幅和时间延迟都要共同考虑。观察整段曲线，比只看最后一个数更容易发现问题。

## 不变量：比“看起来不错”更明确的承诺

这里能直接检查的约束是：每次功率都在 −4～4，历史中始终已有初始温度，延迟索引不会小于零，所有允许输入都在有限次循环内结束。它们称为不变量或边界约束。温度始终等于目标并不是这个模型承诺的性质。

真正工程还要说明采样精度、传感器失效处理、断电恢复、最大允许温度和截止时间。安全不等于任何异常都停止：电梯、电站冷却和呼吸支持系统的安全动作可能不同，需要先分析物理过程。

## 自测：为什么最终数值不能替代全过程

问：两次实验最后都接近目标，能说明它们同样好吗？答：不能。一条可能先冲到很高再回落，另一条可能平稳接近。峰值、响应时间、振荡、能耗和有效范围都可能影响选择。

问：把界面画成恒温箱就成了真实设备模拟器吗？答：没有。只有当方程、参数、时间和验证覆盖了目标设备的相关行为时，才有相应的预测能力。本模块用明确简化的模型帮助理解因果，不把漂亮动画当物理精度。
